# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is the **frontend** of a multiplayer Jeopardy web app: React 19 + TypeScript + Vite, routing with `react-router` v8 (data router), HTTP with axios.

The **backend** is a separate Spring Boot repository in the sibling folder `../backend` (same parent directory as this one), with its own `CLAUDE.md`. **`../backend/docs/api.md` is the contract between the two**: REST and STOMP endpoints, payloads, game session states, timings, error codes and ready-made TypeScript types (section 8). Read it before adding or changing any API call or type. If the frontend needs something the backend doesn't provide, the change belongs in the backend (and its `api.md`), not in a frontend workaround.

## Commands

```bash
pnpm install      # dependencies (run it first in a new worktree)
pnpm dev          # Vite dev server on http://localhost:5173
pnpm build        # type-check (tsc -b) + production build
pnpm lint         # ESLint
pnpm test         # Vitest, once (pnpm test:watch to rerun on save)
pnpm preview      # serve the production build
```

`pnpm build` is also the type check, and it covers the test files.

The package manager is **pnpm** (version pinned by `packageManager` in `package.json`, run through corepack), not npm: don't create a `package-lock.json`. pnpm hard-links packages from one shared store, so installing in each git worktree is fast and takes almost no disk space. Its `node_modules` only exposes declared dependencies, so add a package to `package.json` (`pnpm add`) before importing it.

### Tests

Vitest with jsdom and React Testing Library, configured in the `test` block of `vite.config.ts`. Tests sit next to the code they test (`*.test.ts(x)`) and import `describe`/`test`/`expect`/`vi` from `vitest` explicitly (no globals). `src/test/setup.ts` adds the jest-dom matchers and clears the DOM and `localStorage` after each test; `src/test/fixtures.ts` has `makeSession()`/`makePlayer()` for `GameSession` data.

- Nothing talks to the backend: API modules mock `./client`, and `useGameSession.test.ts` replaces `@stomp/stompjs`'s `Client` with a fake whose callbacks (`onConnect`, `onStompError`, subscriptions) the test calls directly.
- Components that use router hooks or `<Form>` are rendered inside `createMemoryRouter` + `RouterProvider`, with a stub `loader`/`action` where needed.

### End-to-end checks and the Stop hook

- `pnpm e2e` runs `scripts/e2e/` against the real backend through the dev server (both must be running): real STOMP clients play the session rules and a whole Trebek game, then headless Chrome plays a whole game with several players, Trebek included. The `test-live-session` skill (`.claude/skills/`) says when and how to run them.
- `.claude/settings.json` has a Stop hook, `scripts/stop-checks.mjs`, that runs build, lint and tests at the end of a turn when `src/`, `scripts/` or a config file changed since its last run. It's silent when they pass and hands failures back to Claude. Its state is in `node_modules/.cache/claude-stop-checks.json`: delete it to force a rerun.

### Running against the backend

- The backend runs on `http://localhost:8080` (start it from `../backend`; see its CLAUDE.md for the database environment variables).
- `vite.config.ts` proxies `/api` and `/ws` to the backend, so the frontend always uses relative `/api/...` and `/ws` URLs. The target is `BACKEND_URL`, default `http://localhost:8080`. The backend's Kubernetes setup (`../backend/k8s/README.md`) serves both through an Ingress on port 80: start the dev server with `BACKEND_URL=http://localhost` (in PowerShell, `$env:BACKEND_URL='http://localhost'; pnpm dev`).

## Architecture

### Data flow: loaders, not effects

Pages get their data from **react-router loaders**, not `useEffect` fetches. `src/router.tsx` defines the route tree (`/` is the home page, a menu of tiles; `games`, `games/:id`, `clues/:id`, `custom`, `sessions`, `sessions/:id`), and each route's `loader` comes from the matching `src/api/*.ts` module. Pages read it with `useLoaderData() as T` and use `useNavigation()` for pending state.

Loaders validate route/search params themselves and `throw new Response(message, { status: 400 })` on bad input. All route errors (thrown `Response`s and `ApiError`s) render the single root `errorElement`, `src/pages/ErrorPage.tsx`, which distinguishes the two. The backend is often switched off (production puts it behind CloudFront): an `ApiError` with status 0, 502, 503 or 504 means the game server is offline (`isServerOffline` in `src/api/errors.ts`), and `ErrorPage` shows `components/ServerOffline.tsx` with a reload button instead. While the first page's loaders run, the root route's `HydrateFallback` (`src/pages/LoadingPage.tsx`) is shown.

**The whole site looks like the TV show**, like a live game: `src/index.css` styles the browsing pages (black background, blue panels, gold Oswald type; `.site-page`, `.gold-button`, `.outline-button`, `.tv-table`) and `src/tv.css` the live game. The games list (`/games`, the "catalog") and the live games list (`/sessions`) are tables whose column headers sort them (`SortHeader`, `src/api/listSort.ts`) through the `sort` and `direction` search params, which go to the backend as they are: it sorts and filters the whole list before paging (`api.md` §3.1, §3.2), so the pages never reorder what they get. A live game's `stage` (lobby, a round, finished) isn't a response field: `sessionStage` derives it like the backend.

The games list keeps its filters, sort and page in the URL search params (`season`, `title`, `from`, `to`, `sort`, `direction`, `page`); the live games list likewise (`search`, `stage`, `joinable`, `finished`, `sort`, `direction`, `page`). Links from the list pass `{ gamesSearch: location.search }` as router location state (`src/navigation.ts`), and the game and clue pages forward it on their links, so "Back to games" returns to the same filtered page. Keep forwarding `location.state` on any new links between these pages.

### API layer (`src/api/`)

- `client.ts`: one axios instance with `baseURL: '/api'` and a generic `get<T>(url, params)` helper. It converts axios errors into `ApiError` (`errors.ts`) using the backend's `ApiErrorResponse` body (`{status, code, message}`), falling back to the HTTP status (and a `null` code). Decide on an error by its `code` (`hasErrorCode`), not its status: several errors share one (`api.md` §3). Add new HTTP verbs here in the same style rather than calling axios from feature modules.
- One module per backend resource (`games.ts`, `clues.ts`) holding the response interfaces (mirroring the types in `api.md`), the fetch functions, and the route loaders.

### Game board rendering

- `GameResponse` splits categories into `jeopardyRound`, `doubleJeopardyRound` and `finalJeopardy`. The round is derived from `columnNumber` (1–6 Jeopardy, 7–12 Double Jeopardy, 13 Final).
- `GET /api/games/{id}` does **not** return clue values, so `components/GameBoard.tsx` computes them from `columnNumber` and `rowNumber`. Keep this consistent with the backend's rules (`Clue.getValue()` / `api.md`). Rows can have gaps, so the board always renders 5 rows and says "Clue not available" where a category has no clue for that row. The game page shows the rounds one under the other in the session board's style, every clue's text on the board; clicking a clue flips it to its correct response and back ("Show all answers" flips them all). A round or Final Jeopardy without clues is said so in its place.
- Clue questions contain HTML from the database. Render them only with `components/ClueQuestion.tsx` (never `dangerouslySetInnerHTML`): it parses them with `DOMParser` and rebuilds React elements from the tags questions use (`src/clueHtml.tsx`); any other tag shows as text. Every other string (categories, answers, names) is plain text. Clues may carry media (`clueType` `IMAGE` / `VIDEO` / `SOUND` with `mediaUrl`).

### Custom shows

- `/custom` (`pages/CustomShowPage.tsx`, components in `src/components/custom/`, styles in `src/customShow.css`) builds a board in the browser and hosts it (`api.md` §3.2, "Custom shows"). **The backend only sees it when it's hosted**: the draft, undo/redo (`hooks/useDraftHistory.ts`), blind editing, Daily Double pins (1 in Jeopardy, 2 in Double Jeopardy), the Custom and media badges and the file export/import all stay in the frontend. There's one draft per browser, saved to `localStorage` after every change (`loadDraft`/`saveDraft`). The route's loader only fetches a stored game for `?game=<id>`, which "Host custom" in the catalog and on a game page links to: `draftFromGame` turns it into a whole draft (named after the game, its Daily Doubles kept), filling an empty board or asking before replacing one, and the page drops the parameter so a reload doesn't load it again. Category imports use the existing `GET /api/games` (with `finalCategory` for Final Jeopardy) and `GET /api/games/{id}`; a category already on the board (`sourceCategoryId`) can't be imported again.
- `src/api/customShows.ts` holds the request types, the `Draft` model with its pure edit functions, `customGameRequest` (columns and rows stay the board's own, 1-based; an unnamed category without clues is left out; a never-named category is sent with `name: null`; media links go through `mediaLink`) and `customShowAction`, which the page posts to as JSON: it creates the session with `{ customGame }`, joins and redirects like hosting a stored game. A `422 INVALID_CUSTOM_GAME` returns the backend's `problems` (on `ApiError.problems`); the page lists them and marks each place by round/column/row (`components/custom/board.ts`), and `openProblems` drops a problem once its place is edited. The frontend checks nothing else before hosting: the backend decides what's playable.
- Clue text is stored and sent **as written, HTML tags included**, and the editor's previews render it with `ClueQuestion` like the live game. Exported files are `{ format: 'jeopardy-custom-show', version: 1, show: Draft }`, read back field by field with `readDraft`.
- The live games list marks a custom show (`custom`, with `clueCount`) next to its name; it has no season or air date.

### Live game sessions

- **A session's id is a 5-character session code** such as `7KQ2M` (`api.md` §3.2), from Crockford's base32 (no I, L, O or U). `src/sessionCode.ts` makes random codes (`crypto.getRandomValues()`) and normalizes typed ones like the backend does: uppercase, O as 0, I and L as 1. `sessionLoader` validates `/sessions/:id` as a code (400 otherwise) and redirects a non-normalized URL to the normalized one, so the normalized code is what's routed (`?session=`), stored (`localStorage` keys) and shown. The lobby shows the code, and the live games list has a "Join with a code" field (`JoinByCode`), which posts to the `/sessions` action: `sessionsAction` tells it from hosting by its `code` field, checks the session exists and says on the form when the code is malformed or unknown.
- `/sessions` lists live games (its loader). "Host live game" on a game page, "Host" on a games list row and "Host a random game" on the home page (`HostGameForm`) ask for the player's name and post to the same route's action (through a fetcher, so its errors show on the form; a random game is picked there with `getRandomGame`), which creates a session (`PUT` under a random code the client picks, picking another on `SESSION_ALREADY_EXISTS`; `UNPLAYABLE_GAME` shows on the form), joins it and redirects to `/sessions/:id`: hosting is one step. Joining is the `/sessions/:id` action. Both remember the name (`getRememberedPlayerName`) to fill in next time. The first player to join is the host (`hostPlayerId`): only they can start, change the lobby's timers and late-join setting (`allowLateJoin`), and kick players. Each timer saves when the host leaves its field (`TimerSettings`), with no save button. New players start at the session's `joinScore`, and a join the backend refuses (`SESSION_NOT_JOINABLE`) shows on the join form. `isJoinable` mirrors the backend's rule: the lobby, then `allowLateJoin`, and never once Final Jeopardy's wagering is over. Names are capped at `MAX_NAME_LENGTH` and answers at `MAX_ANSWER_LENGTH`, both counted in code points (`textLength`) like the backend. Without a token you're a spectator: `JoinChoice` offers "Join this game" or "Watch as spectator", and a spectator can still join later while joining is allowed. The live games list's Join and Watch links pick the mode through location state (`joinMode`, `src/navigation.ts`), a brand new session (no players yet) opens on the join form, and someone who just left or was kicked stays on as a spectator. `src/api/sessions.ts` holds the session types (mirroring `api.md` §8), the REST calls, the loader/actions, and the player token storage (`localStorage`, keyed by session id), plus the player's own Final Jeopardy wager and answer, which the server hides until the reveal. `forgetPlayer` clears both.
- **Every request about one session carries `?session=<its id>`** (`api.md` §3.2): the create, fetch and join (`routedTo` in `src/api/sessions.ts`) and the `/ws?session=<id>` URL. With several backend instances, the load balancer routes by it to the one holding the session in memory; a single instance ignores it. So a STOMP connection only ever serves the session in its URL. The lobby list and game browsing take no parameter.
- **The player token is a secret**: only ever send it in the STOMP `player-token` CONNECT header. Never display, log, or put it in a URL.
- `src/hooks/useGameSession.ts` owns the STOMP connection (`@stomp/stompjs`, plain WebSocket to `/ws`, forwarded by `vite.config.ts`). The server sends full snapshots, so the hook only keeps the one with the highest `version`, and it fetches the state over REST after every (re)connect. **The hook alone decides when a connection ends for good**: it stops the client, sets status `ended` and calls `onEnded(SessionEnd)` once per mount, with the reason. `left` and `abandoned` (the last player left, which closes the session) come from the hook's own `leave()`, without waiting for the server. `removed` and `rejected` come from a STOMP ERROR, which the backend only sends when a token stops working (any other close, such as missed heartbeats, has none and just reconnects). Heartbeats run in a Web Worker (`TickerStrategy.Worker`), so a hidden tab's throttled timers don't make the server drop the connection. `removed` means the connection was closed after a leave or kick, maybe from another tab sharing the token, and carries the ERROR's message. `rejected` means the token was refused on CONNECT, e.g. the session was lost in a backend restart. `closed` is the `CLOSED` snapshot (the session was removed). `SessionPage.handleEnded` is the one place the token is forgotten: every tab sharing it gets there, so it forgets the stored token only if it's still this tab's (another tab may have joined again), without using storage as an "already handled" flag. Then it revalidates to show the join form or spectator view with a notice (`left`, `removed`), navigates to `/sessions` (`abandoned`), or keeps the final view (`closed`). When the WebSocket fails to connect, the hook fetches the session over REST: if that fails as offline too, it stops reconnecting with status `offline` and the page shows the same offline message. The hook reads its `initial` session only on mount, so `SessionPage` remounts the live view (via `key`) when the token changes.
- Components under `src/components/session/` render from the latest snapshot, switching on `state`. Countdowns come from `phaseRemainingMs` measured from when the snapshot arrived (`receivedAt`, `performance.now()`), never from the client's clock.
- **The live game looks like the TV show** (styles in `src/tv.css`, fonts Oswald, Libre Baskerville and Caveat from Google Fonts in `index.html`). `SessionPage` lays every state out the same way on a black `.tv-stage`: the blue main screen (lobby, `SessionBoard`, `CluePanel`, `FinalJeopardyPanel`, `GameResult`, or a `TitleCard`), then `StatusBar` (a tiny "J!" logo linking home in a new tab, round, whose turn it is from `sessionStatus`, the phase countdown), then `PodiumRow`. Session pages hide the site's top nav (`App.tsx`) to give the game the space. Each `Podium` shows score, lights (counting down the answering or Daily Double player's time) and name; your own has the red `BuzzButton` (pressable any time, it only buzzes while buzzers are open; Space too), and the host gets a kick button on the others. A player without a connection (`away`) is dimmed with an "Away" badge. Daily Double and Final Jeopardy wager limits come from the server (`currentClue.minWager`/`maxWager`, `finalJeopardy.players[].maxWager`). A `TOO_LATE` error (buzzed second, time ran out) is shown as a plain status, not an alert. With more than 4 players your podium is pinned left and the rest scroll to whoever is active. Join as player (spectators, under a "You're watching as a spectator" note), Share link and Leave sit at the row's right, Join goes away once joining closes (`isJoinable`) and Leave from the Final Jeopardy reveal on, since leavers then stay in the results (`leaving`, shown as "Left"); `JoinChoice` is controlled by the page. Every round opens with a title card (`ROUND_INTRO`: only `TitleCard` with the round's name, nothing playable), and a chosen Daily Double is announced (`REVEALING_DAILY_DOUBLE`, in `CluePanel`) before its wager; both last their phase's `phaseDurationMs`, like every other phase (never hard-code durations). A round's card zooms in (`TitleCard`); a picked clue's screen grows out of its cell over the board, which stays behind the screen while a clue is in play, and a Daily Double's rolls forwards once as it grows, or in place if the clue was already on screen (`useClueZoom`, finding the cell by `data-clue-id`). Animations respect `prefers-reduced-motion`. The Final Jeopardy reveal goes one player at a time in `finalJeopardy.revealOrder` (lowest score first), following each player's `revealStep` from the server (`HIDDEN`, `WAGER`, `ANSWER`, `AWARDED`; `revealProgress.ts`), each step its own phase; the server applies each player's score at their award.
- **Hosting as Trebek** (`api.md` §6.8): in the lobby the host picks "Play along" or "Be Trebek" (`hostMode`) and, for a Trebek game, which timers stay automatic (`timerModes`, in `TimerSettings`), all through `update-settings`. Trebek isn't in `players` (`session.trebek`, `isTrebek`): they have no podium or buzzer, a lectern left of the podiums, and `components/session/TrebekDesk.tsx` beside the screen, with the clue and correct response before anyone sees them, `advance` (which also ends a title card or a Daily Double announcement early), rulings (also before an answer is submitted), Final Jeopardy rulings and reveal steps, pause and score changes. Trebek's secrets come only from `/user/queue/trebek`: `useGameSession` returns the `trebekView` whose `version` matches the snapshot, and the desk still checks it against the clue in play. The answer check only suggests; rulings are final (scores are fixed with `adjust-score`). In a Trebek game each Final Jeopardy award waits for Trebek's ruling. Trebek leaving mid-game closes it (`TREBEK_LEFT`); `leavingClosesSession` says when a leave closes the session.
- **Never use `window.confirm`**: some browsers (embedded ones, like the Claude desktop app's) return `false` without showing it. Ask on the page with `ConfirmButton`, as leaving and kicking do. The UI e2e makes `window.confirm` throw.
- There's no winner field: `GameResult` takes the highest final score, with ties.
- Answers are checked on the server (`api.md` §6.7). Don't parse the correct response's notation (`(N of) A | B`, `[A | B]`) in live games: `CorrectResponse` shows what the player who got it right named (`matchedAnswers`, in Final Jeopardy your own if you got it right) plus a list's other options (`alsoAccepted`, "We would also have accepted …"), and otherwise the clue's `acceptedAnswers` (formatters in `src/format.ts`). The browsing pages' clues have no `acceptedAnswers`, so they still use `formatCorrectResponse`. `AnswerForm` warns when only an exact number counts (`numberExpected`). The question form is only mentioned after an answer, from its `phrasedAsQuestion`: `ClueAnswers` warns the player who left it out in the Jeopardy round, and from Double Jeopardy on marks a wrong answer "not phrased as a question" (also in the Final Jeopardy table). `clueAnswersRound` says which round the answers on screen belong to.

## Code style

Matches the existing code: no semicolons, single quotes, 2-space indentation, function components with a default export, props typed with a `<Name>Props` interface, `import type` for type-only imports (`verbatimModuleSyntax` is on). TypeScript has `noUnusedLocals` / `noUnusedParameters` enabled, so the build fails on unused code.
